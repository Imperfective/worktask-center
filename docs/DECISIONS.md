# 판단 기록

구현 중 내린 판단을 시간순으로 남긴다. 각 항목은 **결정 / 고려한 대안 / 이유 / 결과** 순.

---

### 1. 문제의 원인을 "채널"이 아니라 "객체 부재"로 봤다
- **대안** 메신저 봇·메일 파서를 만들어 기존 채널을 자동화
- **이유** 새 채널을 하나 더 만들면 흩어짐이 늘어난다. 요청이 ID·상태·담당자를 갖는 순간
  누락·가시성·기록이 같은 구조에서 함께 풀린다.
- **결과** 유지. 알림·메일 연동을 범위에서 제외하는 근거가 됨.

### 2. 상태를 6개로 두고 "배정"을 상태로 만들지 않았다
- **대안** 접수 → **배정** → 처리중 으로 7단계
- **이유** 담당자 지정 여부는 담당자 필드로 이미 보인다. "내가 맡기" 한 번으로 배정과 착수가
  함께 일어나므로 둘 사이에 상태가 있을 필요가 없다.
- **결과** 유지. `assign` API가 접수 상태면 처리중으로 함께 전이한다.

### 3. 반려를 종착 상태에서 뺐다
- **대안** 반려는 최종 상태, 이의가 있으면 새로 등록
- **이유** 재등록하면 기록이 끊긴다. 같은 타임라인에 이어 붙는 편이 "기록" 목표에 맞다.
- **결과** 유지. 반려 → (다시 요청) → 처리중 전이를 추가.

### 4. 전이 검증을 서버 한 곳(전이 맵)으로 모았다
- **대안** 화면에서 버튼 노출 조건을 따로 쓰고 서버에서도 따로 검증
- **이유** 규칙이 두 곳에 흩어지면 화면과 서버가 어긋난다. 이런 시스템의 가장 흔한 결함이다.
- **결과** 유지. 상세 API가 전이 맵으로 계산한 *허용 액션*을 내려주고, 화면은 그대로 버튼으로 그린다.

### 5. 이벤트를 추가 전용으로 두고 코멘트도 이벤트로 저장했다
- **대안** comments 테이블 분리
- **이유** 타임라인의 원천을 하나로 유지해야 "무엇이 언제 일어났나"가 한 줄로 읽힌다.
- **결과** 유지. `request_events` 하나에 상태 전이·배정·코멘트·참여·AI 제안이 모두 쌓인다.

### 6. 상태·담당자를 이벤트에서 재구성하지 않고 컬럼으로도 들고 있다
- **대안** 이벤트만 두고 현재 상태는 매번 계산
- **이유** 목록 조회가 단순해진다. PoC 규모에서 재구성 비용을 낼 이유가 없다.
- **결과** 유지. 쓰기 시 두 곳을 같은 요청 처리 안에서 갱신한다.

### 7. AI를 자동 배정·자동 완료에 쓰지 않았다
- **대안** 카테고리로 담당자까지 자동 지정
- **이유** 잘못된 배정은 누락보다 발견하기 어렵다. 처리 책임이 사람에게 있어야 기록을 신뢰할 수 있다.
- **결과** 유지. AI는 제안만 하고, 부서 라우팅은 카테고리 규칙으로 충분했다.

### 8. 긴급도에 "판단 근거 한 문장"을 함께 제안하게 했다
- **대안** 긴급도 값만 제안
- **이유** 요청자가 긴급도를 고칠 때 근거가 없으면 판단할 수 없다. 긴급 남발도 막는다.
- **결과** 유지. `urgency_reason`을 스키마와 프롬프트에 고정.

### 9. 한 줄 요약만 읽기 전용으로 두고 나머지는 모두 수정 가능하게 했다
- **대안** AI 제안 전체를 잠금 / 전체를 수정 가능
- **이유** 목록·상세 표기를 일정하게 유지하려면 요약은 고정이 낫다. 반대로 분류가 틀렸을 때
  사용자가 손쓸 방법이 없으면 안 되므로 제목·카테고리·긴급도는 열어 둔다.
- **결과** 유지.

### 10. AI 백엔드를 Anthropic API → Ollama 로컬 모델로 바꿨다
- **대안** Anthropic Messages API (원래 설계)
- **이유** 분류·유사도 판단은 추론 깊이보다 응답 속도가 중요하고, 내용이 단순하다.
  로컬 모델이면 API 키 관리·키 노출 위험·외부 의존이 모두 사라진다.
- **결과** 유지. `qwen2.5:1.5b`(986MB)로 CPU 추론. 타임아웃은 로컬 CPU를 감안해 8초 → 20초로 늘렸다.

### 11. 런타임 이미지에서 Prisma CLI를 뺐다
- **대안** 컨테이너 기동 시 `prisma db push` + 시드 실행 (첫 시도)
- **이유** 첫 배포에서 `MODULE_NOT_FOUND`로 재시작 루프에 빠졌다. standalone 산출물에는
  CLI 의존성 트리가 들어 있지 않다.
- **결과** **번복.** 빌드 시점에 스키마+시드까지 끝낸 DB를 템플릿으로 굽고,
  런타임에는 볼륨에 없을 때만 복사한다. 이미지가 가벼워지고 기останов 시간이 72ms로 줄었다.

### 12. 포트를 열지 않고 도커 네트워크로만 붙였다
- **대안** `ports: 3300:3300` 후 호스트 경유 프록시
- **이유** 이 서버는 이미 다른 서비스가 도는 운영 서버다. 포트를 늘리면 노출면이 넓어진다.
- **결과** 유지. 기존 caddy를 앱 네트워크에 연결해 컨테이너 이름으로 프록시한다.
